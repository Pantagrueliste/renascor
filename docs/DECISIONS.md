# Design decisions

This document records non-obvious choices made when building Renascor, and the reasoning behind them. It is intended for future maintainers and curious contributors.

## Data format: JSON, not YAML

Each catalogue entry is a single JSON file. We chose JSON over YAML for three reasons:

1. **No extra dependency.** JSON is parsed natively by Python (stdlib `json`) and by every browser. YAML requires PyYAML or a browser-side library.
2. **Schema validation.** JSON Schema is a mature standard with validators in every language. There is no equivalent widely-adopted schema language for YAML.
3. **Static site.** The public site loads entries in the browser. JSON needs no transformation; YAML would require a build step or a client-side parser.

The cost is verbosity: JSON is less compact than YAML and does not support comments. For a catalogue of a few hundred entries, this is acceptable.

## One file per entry

Each entry lives in its own file under `data/entries/`, named after the project (for example, `textgrid-repository.json`). We chose this over a single monolithic `data.json` because:

- **Merge conflicts.** Two contributors adding entries rarely touch the same file.
- **Git history.** Changes to one entry are easy to trace.
- **Partial validation.** The CI can validate only the files changed in a pull request.

The public site is generated by a build script (`scripts/build_site.py`) that collects all entries into a single `data.json` for the browser.

## Licences: CC0 for data, MIT for code

The data is released under **CC0 1.0 Universal**. A catalogue is most useful when it can be reused without friction: merged into other databases, loaded into a spreadsheet, redistributed. CC0 removes all copyright restrictions and any obligation to attribute.

The code is released under the **MIT Licence**. MIT is permissive, well understood, and compatible with almost everything. It requires only that the copyright notice be preserved.

We use two separate licence files (`LICENSE` and `LICENSE-DATA`) rather than one combined file because the distinction matters: a contributor reading `LICENSE` should know immediately which licence applies to their work.

## No database

Renascor is a directory of JSON files, not a database. There is no SQL, no server, no API. The dataset is small (expected: hundreds to low thousands of entries) and changes slowly (a few entries per week at most). A database would add operational cost with no benefit at this scale.

If the catalogue grows to tens of thousands of entries, this decision should be revisited.

## Static site, no framework

The public site is a single HTML page with vanilla JavaScript. We chose this over a framework (React, Vue, Svelte) because:

- The site is simple: a searchable, filterable table.
- Vanilla JS has no build step and no dependency tree.
- The page loads fast and works without JavaScript for basic viewing (the data is in a `<script>` tag, but the table is server-rendered at build time).
- Accessibility is easier to control when the HTML is hand-written.

The build script (`scripts/build_site.py`) generates the HTML table from the JSON entries. The JavaScript handles only search and filtering client-side.

## Weekly discovery, human review

An automated agent discovers new candidate entries each week. These are **never** merged automatically. The agent opens an issue labelled `discovered`, and a human reviews each candidate before it enters the catalogue.

This is deliberate. Automated discovery finds candidates; it does not judge quality, scope, or accuracy. A human must confirm that a project is real, relevant, and correctly described.

## Minimal dependencies

The Python dependencies are limited to `jsonschema` (validation) and `requests` (HTTP checks). Everything else uses the standard library. This keeps the project cheap to run and easy to audit.

The GitHub Actions use only official actions (`actions/checkout`, `actions/setup-python`) plus `pip install` for the two dependencies above.
